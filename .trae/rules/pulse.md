# 软件工程流程与规则规范

> 用途：开发智能体的「施工规范手册」，贯穿需求分析 → 架构设计 → 前后端开发 → 自测 → 测试 → 发布全流程  
> 目标：保证功能完整性、输出质量，杜绝缺服务/缺页面/缺跳转/接口丢失/前后台不一致/数据不落库等低级问题

---

## 一、总纲：防低级错误的六大铁律

开发智能体在任何阶段都必须遵守。违反任意一条，交付即不合格。

| 铁律                      | 防止的低级问题                                               |
| ------------------------- | ------------------------------------------------------------ |
| **1. 前后端成对交付**     | 有接口必有前端页面调用，有前端操作必有后端支撑，不交付「半截」功能 |
| **2. 页面必有路由和跳转** | 每个页面有路由，每个动作有出口，无 404 死链                  |
| **3. 接口必有映射**       | 每个接口在「页面↔接口↔跳转」映射表中有对应记录               |
| **4. 前后台同步更新**     | 客户端改了什么，管理端同步改，不允许两端不一致               |
| **5. 数据必落库**         | 每个表单提交/状态变更必须持久化到数据库，不做纯前端假数据    |
| **6. 端到端验收**         | 以「用户完整旅程」验收，不以「接口调通」验收                 |

---

## 二、六阶段流程总览

```
阶段1 需求分析 ──▶ 阶段2 架构设计 ──▶ 阶段3 前后端开发 ──▶ 阶段4 自测 ──▶ 阶段5 测试 ──▶ 阶段6 发布
   │                  │                    │                │            │              │
  产出:              产出:                产出:            产出:        产出:          产出:
  需求清单           施工图(状态机/DDL/    前后端代码       自测报告     测试报告       发布清单
  + 用户旅程图       API/页面/跳转表)      + 路由表                        + 验收记录
```

**关键原则：前一阶段的产出是后一阶段的输入，缺一不可。任何阶段产出不完整，不得进入下一阶段。**

## 三、阶段 1：需求分析

### 输入

PRD 文档、原型图、系统总览

### 必做动作

```
1. 读懂需求，明确「为谁做、解决什么问题」
2. 画出用户旅程图（用户从哪进来 → 做什么 → 得到什么结果）
3. 提取「入口/动作/出口」三元组（每个功能）
4. 识别涉及的角色（personal/school/enterprise）和权限差异
5. 识别涉及的状态流转、数据表、资金规则
6. 标注模糊点、矛盾点，反馈人类确认（不硬写）
```

### 产出

```markdown
## 需求清单
### 用户旅程图
[入口 → 动作 → 出口 的完整链路]

### 功能点清单
| 功能 | 角色 | 入口 | 动作 | 出口 | 涉及状态 | 涉及表 |

### 待确认问题
[模糊点/矛盾点，需人类拍板]
```

### 防错关卡

```
□ 每个功能都有「出口」吗？缺出口 = 需求理解不全
□ 三种角色的权限差异都理清了吗？
□ 有没有遗漏管理端的需求？（用户可见功能往往有对应后台配置/审核）
```

## 四、阶段 2：架构设计

### 必做动作

```
1. 设计状态机（状态列表 + 转换条件 + 非法转换防御）
2. 设计数据库表（DDL + 索引 + 约束）
3. 设计 API（URL/方法/参数/返回/错误码/权限）
4. 设计页面清单（前端每个页面 + 路由）
5. 设计「页面↔接口↔跳转」映射表
6. 设计前后台一致性方案
```

### 产出

```markdown
## 施工图
### 1. 状态机设计
### 2. 数据库 DDL
### 3. API 清单
### 4. 前端页面 + 路由清单
### 5. 页面↔接口↔跳转映射表（核心！）
### 6. 管理端同步清单
### 7. 人工决策点（需人类拍板）
```

### 核心产出：页面↔接口↔跳转映射表

这是防「接口丢失、跳转丢失」的关键，必须完整：

```markdown
| 页面/路由 | 触发动作 | 调用接口 | 成功后的跳转/状态变化 |
|-----------|---------|---------|---------------------|
| /market | 点「发布机会」 | — | 跳转 /publish |
| /publish | 点「直接发布」 | POST /projects | 跳转 /payment 交付预付款 |
| /payment | 点「提交付款」 | POST /payments | Toast 发布成功，跳 /my-opportunities |
| /detail/{id} | 点「参与竞标」 | — | 跳转 /bid/{id} |
| /bid/{id} | 点「提交竞标」 | POST /bids | 回详情页，竞标数+1 |
```

### 防错关卡

```
□ 前端页面清单完整吗？有没有页面缺路由？
□ 每个 API 都在映射表里被某个页面调用了？有没有「孤儿接口」？
□ 每个页面动作都有明确出口？有没有「死胡同页面」？
□ 管理端有没有需要同步的字段/状态/通知？
```

## 五、阶段 3：前后端开发

### 后端开发规则

```
1. 分层规范：
   Controller（参数校验、调 Service、返响应）
   → Service（业务逻辑、事务）
   → Repository（数据访问）
   ❌ 禁止 Controller 直接调 Repository，禁止 Service 返回 HTTP 类型

2. 数据持久化（铁律 5）：
   每个「写入」操作必须有对应的 insert/update
   ❌ 禁止只在内存/前端改，不落库
   ✅ 状态流转必须 update 数据库字段

3. 金额与精度：
   金额用 BigDecimal（或 long 分），禁用 float/double

4. 统一响应：
   R<T> { code, message, data, timestamp }

5. 异常处理：
   全局异常处理器，不返回裸堆栈

6. 事务边界：
   多步写操作（资金流转、状态变更+记录）必须 @Transactional
```

### 前端开发规则

```
1. 路由完整性（铁律 2）：
   每个页面注册路由，每页有「返回」入口
   ❌ 禁止有组件无路由、有页面无入口

2. 跳转逻辑（铁律 2/3）：
   每个按钮/操作都绑定明确的跳转或状态反馈
   提交成功后必须跳转 + 刷新数据（不能只弹个提示就完了）

3. 接口调用完整性（铁律 3）：
   页面操作必须真实调用后端接口
   ❌ 禁止前端写假数据、写死返回值

4. 状态同步：
   接口成功后同步刷新（列表、计数、状态标签、余额）

5. 权限差异（铁律 4）：
   不同角色渲染对应页面/按钮
   （企业看不到简历入口、个人看不到企业管理后台）

6. 视觉规范：
   对齐 token，禁止自行改样式
```

### 防错关卡

```
□ 后端每个接口都有对应的前端调用吗？（扫「孤儿接口」）
□ 前端每个操作都调了真实接口吗？（扫「假数据」）
□ 每个表单提交都落库了吗？（扫「不落库」）
□ 前端路由表完整吗？（扫「死链」）
□ 三种角色各渲染对了吗？（扫「越权/错位」）
```

## 六、阶段 4：自测（开发完成即做）

开发智能体在交付前，必须自己测一遍：

### 自测清单

```
□ 单元测试：核心逻辑（金额计算、状态流转、权限判断）
□ 接口自测：每个接口用真实请求测通，确认返回结构正确
□ 数据落库自测：提交表单 → 查数据库 → 确认数据真实写入
□ 跳转自测：从入口点到出口，确认每一步跳转正确
□ 角色自测：切三种角色，确认各自看到正确的页面/按钮
□ 状态自测：走一遍状态流转，确认每个状态变化正确落库
□ 边界自测：空数据、超长输入、非法输入、重复提交
```

### 产出：自测报告

```markdown
## 自测报告
| 测试项 | 结果 | 说明 |
|--------|------|------|
| 数据落库 | ✅ | 提交后 projects 表新增记录 |
| 跳转链路 | ✅ | 市场→详情→竞标→回详情 |
| 角色权限 | ✅ | 企业看不到简历入口 |
```

## 七、阶段 5：测试（E2E + 关键旅程）

### 测试重点：不是只测单接口

```
1. 单元测试：JUnit 5（后端）+ Vitest（前端）
2. E2E 测试：Playwright 覆盖关键用户旅程

E2E 用例必须覆盖完整旅程，例如：
「登录 → 进机会市场 → 点项目 → 提交竞标 → 断言详情页竞标数+1
  → 断言审批页出现该竞标」
```

### 测试范围

```
□ 每个核心功能至少一条 E2E 用例
□ 每种角色至少一条权限 E2E 用例（验证越权被拦截）
□ 资金相关功能必须有事务一致性测试（不丢钱、不双花）
□ 前后台一致性测试（客户端操作后管理端数据同步）
```

## 八、阶段 6：发布

### 发布前必查清单

```
□ 前端路由表完整，无 404 死链
□ 所有接口有前端调用，无孤儿接口
□ 页面↔接口↔跳转映射表完整
□ 数据落库验证通过（不是假数据）
□ 三种角色权限正确
□ 管理端与客户端一致
□ 单测 + E2E 全部通过
□ 资金/支付代码通过安全审计
□ 视觉规范对齐（无自行改样式）
□ 端到端用户旅程走通
```

### 发布后

```
□ 记录版本号、变更内容
□ 监控异常（接口报错、页面崩溃）
□ 收集用户反馈
```

## 九、防低级错误专项（对照自查）

| 低级问题     | 根因           | 防错机制                                  |
| ------------ | -------------- | ----------------------------------------- |
| 缺前后端服务 | 只写一端       | 铁律1：前后端成对交付，验收时两端都要有   |
| 缺前端页面   | 页面清单不全   | 阶段2产出页面清单，阶段3逐页勾销          |
| 缺跳转逻辑   | 拆任务按接口拆 | 铁律2/3：按旅程拆 + 三元组 + 映射表       |
| 接口丢失     | 接口没被调用   | 阶段3扫「孤儿接口」                       |
| 前后台不一致 | 只改客户端     | 铁律4：架构设计阶段就列「管理端同步清单」 |
| 数据不落库   | 前端假数据     | 铁律5：自测阶段强制「查库验证」           |

## 十、交付物完整性清单（最终把关）

开发智能体每次交付，必须附上以下清单，全部勾选才算完成：

```markdown
## 交付清单
### 前端
- [ ] 页面清单完整，路由已注册
- [ ] 跳转逻辑完整，无死链
- [ ] 每个操作调用真实接口（无假数据）
- [ ] 三种角色渲染正确
- [ ] 视觉规范对齐

### 后端
- [ ] 接口清单完整，无孤儿接口
- [ ] 数据持久化正确（提交即落库）
- [ ] 分层规范（Controller/Service/Repository）
- [ ] 金额用 BigDecimal
- [ ] 事务边界正确

### 数据
- [ ] 表结构完整（DDL + 索引 + 约束）
- [ ] 迁移脚本可用
- [ ] 种子数据可跑通

### 测试
- [ ] 单元测试通过
- [ ] E2E 用例覆盖关键旅程
- [ ] 数据落库已验证

### 一致性
- [ ] 页面↔接口↔跳转映射表完整
- [ ] 管理端与客户端同步
- [ ] 端到端用户旅程走通
```

## 十一、Pulse 项目特定约束（所有阶段都要遵守）

```
角色：personal / school / enterprise（权限差异必须处处体现）
状态机：draft → bidding → reviewing → awarded → executing → milestone → pending_done → completed
资金：服务费10%、保证金1%（500-1000）、资金托管（金额用 BigDecimal）
视觉：token 不可改、居左对齐、Georgia 标题（视觉铁律）
架构：前后端分离 + 契约驱动
管理端：客户端更新必须同步管理端（platform/ 子目录）
```
