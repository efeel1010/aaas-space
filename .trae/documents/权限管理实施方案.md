# 权限管理实施方案（参考飞书文档/知识库/团队空间）

## Context（背景）

Pulse-Space 目前只在**团队级（team_members 角色）+ 分享链接（read/edit）**两个维度做文档访问控制，`findDoc` 只区分"能否访问"（团队→成员，个人→owner），不区分读写，也没有文档级的「开放范围 / 基础角色 / 指定成员」能力。用户希望引入飞书式三层权限：**文档/知识库逐篇权限、团队成员角色继承、团队内部可见范围细分**，粒度为「知识库统一默认 + 单篇覆盖」。

目标：在一套 documents 权限模型上打通「谁能看/谁能改/谁能管」，并同步到管理端与目录树。

已与用户确认的决策：
- **删除/恢复/彻底删除**从"任意团队可删"收紧为 **manage 级**（owner 或团队 owner/admin）。
- 子页仅**继承父级的 visibility/base_permission 列**；逐成员白名单（document_access）**逐篇独立**，不递归复制。

## 1. 数据库增量（apps/api/src/db/schema.ts）

新增枚举：
```ts
export const docVisibilityEnum = pgEnum('doc_visibility', ['private', 'team', 'public']);
export const docBasePermEnum   = pgEnum('doc_base_permission', ['read', 'edit']);
export const docAccessPermEnum = pgEnum('doc_access_permission', ['read', 'edit', 'manage']);
```
`documents` 新增两列：
```ts
visibility: docVisibilityEnum('visibility').notNull().default('private'),
base_permission: docBasePermEnum('base_permission').notNull().default('edit'),
```
新增逐成员授权表：
```ts
export const documentAccess = pgTable('document_access', {
  doc_id: uuid('doc_id').references(() => documents.id, { onDelete: 'cascade' }).notNull(),
  user_id: uuid('user_id').references(() => users.id, { onDelete: 'cascade' }).notNull(),
  permission: docAccessPermEnum('permission').notNull().default('read'),
  granted_by: uuid('granted_by').references(() => users.id, { onDelete: 'set null' }),
  created_at: ..., updated_at: ...,
}, (t) => [{ pk: { name: 'document_access_pk', columns: [t.doc_id, t.user_id] } }]);
```

**迁移（向后兼容，分三步）**：`drizzle-kit generate` 以可空列 + 建枚举/表 → 写 backfill SQL（`team_id IS NOT NULL → team/edit`，`team_id IS NULL → private/edit`，使存量行为=现状最宽松权）→ `ALTER ... SET NOT NULL` 并设默认。

语义：`private`=仅 owner+白名单；`team`=团队成员按 base_permission 可见；`public`=预留枚举（本期不开放 UI）。

## 2. 权限解析算法

新模块 `apps/api/src/lib/docAccess.ts`：
```ts
export type EffectivePermission = 'none' | 'read' | 'edit' | 'manage';
export async function resolveDocAccess(userId, doc, ctx?): Promise<EffectivePermission>
export async function loadDocAccessCtx(userId, docIds, teamIds): Promise<{teamRoleByTeam, aclByDoc}>  // 批量防 N+1
export async function filterAccessible(userId, docs): Promise<DocRow[]>  // 列表过滤
```
解析顺序：`owner → manage`；`teamRole ∈ {owner,admin} → manage`；命中 `document_access → its permission`；`private → none`；`team 成员 → base_permission`；`public → base_permission`；否则 `none`。取各命中的最大权限（maxPerm）。

**操作门禁**：
- 读（详情/版本/评论/收藏/反向链接/祖先链/分享查询）：`read`
- 写（PATCH 内容/移动/重命名/分享增改/评论/另存模板/版本）：`edit`
- 管理（DELETE/restore/permanent、改 visibility/base_permission、增删授权）：`manage`

扩展 `findDoc`（documents.ts L57-69）返回 `effectivePermission`，`none` 统一 403。

## 4. 后端增量（apps/api/src/routes/documents.ts + search.ts）

- **PATCH /documents/:id**：当 body 含 `visibility/base_permission` 时需 `manage`；字段随现有 patch 落库。
- **GET /documents/:id/access**（manage）：返回授权成员（join users+teamMembers）。
- **PUT /documents/:id/access**（manage）：upsert 单成员授权（个人文档可授权任意系统用户，团队文档限团队内成员）；`SetDocAccessRequest`。
- **DELETE /documents/:id/access/:userId**（manage）：移除授权。
- **create**：子级继承——`body.visibility ?? parent.visibility ?? (scope==='team' ? 'team' : 'private')`；base 同理（`parent ?? 'edit'`）。
- **列表过滤**：`GET /` 团队分支与 `/wiki-toc` 用 `filterAccessible` 剔除无权限文档；`/wiki-toc` 输出 visibility/effective_permission。
- **delete/restore/permanent**：门禁改为 `effectivePermission === 'manage'`。
- **search.ts**：doc 命中增加 `document_access` 白名单（`user_id`），覆盖"非 owner 被授权"。
- **toDto**（documents.ts L39-55）补三个权限字段。
- **admin.ts documents**（L149-179）：select 补 `visibility, base_permission`。

## 5. 前端增量

### apps/web/src/lib/api.ts `docApi`
新增 `access(id)`、`grantAccess(id,userId,permission)`、`revokeAccess(id,userId)`。

### DocEditor.tsx —— 「权限」弹窗 `PermissionMenu`
复用 `ShareMenu`（L301-400）的命令摸边关闭交互，工具栏加入口。内容（需 `manage` 才可交碰）：
1. 可见范围 radio：private / team /（public 灰）
2. 基础权限 select：read / edit
3. 指定成员列表（name/avatar/team_role），每人改权限 + 删除；底部用 `UserPicker`（`authApi.searchUsers`）添加成员并指定权限
4. 继承提示：默认"继承父级"，手动改后"自定义"
变更调 `PATCH` + `grantAccess/revokeAccess`，成功后 `qc.invalidateQueries(['doc', id])`。

### 只读门禁 + 目录树标识
- `effective_permission === 'read'`：禁编辑/保存/删除/权限弹窗，只读预览。
- `WikiSidebar.renderNode`：`visibility==='private'` 或 `effective_permission==='read'` 时在书名前加小锁/小眼图标（token 不变）。

## 8. 实施步骤（六阶段，各带验证点）

- **A DB**：schema 枚举/列/表 + 三步迁移 + backfill 幂等；`db:migrate` 后 `\d documents` 核对。

- **D 前端**：`docApi` + `PermissionMenu` + 只读门禁 + 目录树锁标识。
- **E 管理端**：`DocumentsPage` 可见性列。
- **F 自测/测试/验收**：单测/契约/API/E2E；「页面↔接口↔权限」映射自查；端到端旅程（owner 设权限 → 成员被只读/读/拒绝 → 目录树锁 → 管理端列可见）。
